# GATE G5 — StarCraft II `.m3` animation corpus (M3_ANIMATION_PLAN.md §2.2).
#
# Paths are relative to C:/Projects/WhiteoutLib/Corpus, same root as
# corpus_m3.txt. What is different is the rest of the line: a scripted scenario,
# because spawning an `.m3` and letting it run reaches one steady layer and
# nothing else. Cross-fades, layered plays and the weight budget only exist once
# something asks for a second sequence, so the corpus has to ask.
#
#   anim=<path>               attach an `.m3a` (corpus-relative) before anything
#                             else, so `seq=` resolves against the merged list
#   seq=<index|name>          which sequence to start in
#   switch=<frame>:<seq>      SetActiveSequence at that capture frame — a cut
#                             for wc3/wow, a cross-fade for M3
#   layer=<frame>:<seq>       stack a second play at that frame — the only
#                             route into the blender
#   blend=<ms>                blend-in for the layered play (default 250)
#   weight=<f>                its weight (default 1.0)
#
# `seq` matches an index if it parses as one, else a case-insensitive substring
# of the sequence name, with `+` standing in for a space ("Attack+02"). Names
# rather than indices on purpose: indices are export order and shift between a
# unit and its skin variants. `--draw-trace-anim-list` prints the table (and the
# bone count) for any model — that is how this file was curated, and how to
# re-curate it if a name here stops resolving.
#
# Frames assume the arm's 120-frame default at a fixed 60 Hz, so frame 40 is
# 667 ms — past a 150 ms cross-fade's settle, with room for the next event.
#
# Run with (needs a build configured -DWDX_ENABLE_M3=ON):
#   scripts/render-diff.ps1 -Record -Golden -M3Anim
#   scripts/render-diff.ps1 -Check  -Golden -M3Anim
#
# UNLIKE every other arm, these baselines are PROGRESSIVE: each animation phase
# legitimately changes what M3 draws. A diff here is a question, not a verdict.

# the result is a real blend rather than the top layer winning outright.
Sc2M3/Ultralisk.m3       seq=Walk  layer=70:Attack weight=0.5
Sc2M3/BattleCruiser.m3   seq=Stand

# upper-body container while the legs keep their own.

# --- solver models, traced before the solvers exist -----------------------
# Both are here from P-A0 rather than from P-A7 on purpose: the baseline that
# proves a solver changed something has to predate the solver. Colossus names
# `Attack+02`: a bare "Attack" would match "Attack Ready Channel" first, and
# the two are different animations.
Sc2M3/Colossus.m3        seq=Walk  switch=60:Attack+02
Sc2M3/SiegeTank.m3       seq=Stand switch=50:Attack
# The turret case. SiegeTank above carries no PATU chunk despite the name —
# its barrel is animated, not solved — so it covers nothing for `-Solvers`.
# Autoturret does, with exactly one behaviour on bone 2.
#
# Read its `-Solvers` result carefully: the turret demonstrably moves the pose
# (`--draw-trace-anim-probe` shows a different bone hash with the stage on) but
# the GOLDEN is identical to the solvers-off run, because bone 2 drives no
# visible geometry. So this entry proves the stage runs on real chunk data
# without exploding; it does not prove the turret looks right. The turret's
# arithmetic is covered by m3_solver_test, and only there.
#
# Of the whole corpus, only Colossus shows a solver in the image — it is the
# IKJT model, and the one entry that makes `-Solvers` non-vacuous.
Sc2M3/Autoturret.m3      seq=Stand

# --- `.m3a`-driven models -------------------------------------------------
# Every entry above is a self-animated `.m3`, which is a coverage hole rather
# than a choice: a Heroes hero ships its geometry and its animation in separate
# files, and NOTHING above exercises that join. The hole had teeth. A model with
# no `SEQS` of its own also ships every bone AnimRef with the `interpType` u16
# zeroed, and reading that zero as "step" (rather than the engine's only rule,
# `flags & 0x10`) stepped 75.5% of bone SRT refs on these models while leaving
# every model above untouched — a visible tremor no baseline here could see.
#
# Jaina is the case that surfaced it: 139 bones, 0 sequences, 51 arriving from
# the `.m3a`. The two scenarios cover the plain playhead and the blender.
HotSM3/Storm_Hero_Jaina_Base.m3   anim=HotSM3/Storm_Hero_Jaina_RequiredAnims.m3a seq=Stand+Ready switch=45:Walk
HotSM3/Storm_Hero_Jaina_Base.m3   anim=HotSM3/Storm_Hero_Jaina_RequiredAnims.m3a seq=Walk layer=50:Attack weight=0.5

# --- not covered, and why -------------------------------------------------
# §2.2 also asked for a >256-bone model, to exercise the Path A/Path B palette
# split. There is no such M3 case to find: `.m3` stores its vertex bone indices
# region-local, so `DecidePaletteLayoutAndRewrite` forces Path B for every M3
# model regardless of size, and the branch the requirement was aimed at has no
# M3 arm at all. The remaining cap is `bls::kMaxBones` (256) per *geoset*
# palette, which `WriteBonePalette` silently clamps to; the heaviest model here
# is Thor at 139 bones total, so nothing in this corpus reaches it. Finding a
# model that does is worth doing — the failure mode is a wrong pose, not a
# crash — but it is a separate hunt from this gate.
